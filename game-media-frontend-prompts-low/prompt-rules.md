# 提示词规则

按 SKILL.md 的查找顺序读取 `mb.md`。数量、标题和单条版式以它为准。题目内容必须来自刚创建的项目，不能改写 `mb.md` 里的像素画需求。

## 文件

项目根目录只放这一份提示词：

```text
{项目编号}_提示词_{MMDD}.md
```

例如项目编号 `jdk-001`、日期 11 月 12 日，文件名是 `jdk-001_提示词_1112.md`。

版式固定为：

```markdown
**0-1代码生成**

1. 【困难】一整段用户能读懂的需求。

**Feature迭代**

1. 【困难】一整段用户能读懂的需求。

**Bug修复**

1. 【困难】一整段用户能读懂的需求。
```

0-1 代码生成 10 条，Feature 迭代 10 条，Bug 修复 2 条。每条单独占一行，编号在各自小节内从 1 开始。正文不要标题、粗体、列表和代码块。

## 三类题目

- 0-1 代码生成：仓库里还不存在的完整能力，并接到现有模块的数据上。不要写脚手架，也不要把一个新按钮写成 0-1。写之前搜索源码，确认该能力确实不存在。
- Feature 迭代：现有能力不够用，在不推翻已有行为的前提下扩展。写清现在是什么样，扩展后旧数据和新操作怎么相处。
- Bug 修复：只写最终基线中已复现并完成参考修复验证的那 2 个真实缺陷。先读到错误分支，再翻译成用户看到的现象。不能把新增能力或文案调整当成 Bug。

## 困难门槛与范围

同时执行 [范围控制规则](references/compact-scope.md)。所有类别都优先选择“多模块整合 + 关键设计取舍”；当业务确实需要复杂技术时，只处理一个已具备基础设施的明确过程，不叠加新算法或新引擎研发。至少两项困难证据仍必须真实成立。

每条真实难度都是困难，并且正文里能直接看出下面 3 项里的至少 2 项。只贴「兼容」「一致」「校验」不算命中。

- 多模块整合：写清至少两个业务环节如何交接，谁产生数据、谁使用数据，冲突时以哪一处为准，哪些界面一起变化。
- 关键设计取舍：写出两个都说得通的做法，本题选哪一个，另一个会带来什么后果。选择会影响数据模型、状态一致性、资源成本或失败恢复；按钮文字、颜色和排版的选择不构成关键设计取舍。不强制固定句式。
- 复杂技术关注点：写清一个具体触发过程，例如旧文件迁移、损坏内容、撤销历史、播放中编辑、大尺寸合成、重复操作或坐标换算，并写明这个过程里必须保住的结果。

Feature 迭代和 Bug 修复同时还要能看出三件事：用户动作经过哪些环节落到哪个结果；冲突或失败时走哪条路；一个会改变实现的边界发生时，用户看到什么、数据变成什么。

每条正确实现实质新增或修改 5–7 个业务源文件，分别记录路径、改动类型、职责及不可省略的理由。新增文件允许尚不存在，修改文件必须在最终基线存在。测试、样式、配置、锁文件、纯转导出和格式调整不计。不要为了五文件门槛强行修改所有层或破坏高内聚；先尝试共享函数、复用接口等更少文件的正确方案，如果能用不到五个文件完整满足需求，就换题。

题目正文的困难证据必须对应实际新增/变化的数据流、技术过程和验收结果。说“其他模块保持不变”不算整合，提到“播放/旧数据”但不改变相关处理不算复杂技术。纯文案、单点开关、小字段增删、可在一个公共函数解决的简单 Bug，不能靠加长题面或贴【困难】标签升级。

每题还要满足一个连贯的用户目标，不能拼接五个无关小改凑难度。所有题目均从同一个基线独立实施，不能让迭代题依赖某道尚未完成的 0-1 题。

## 写法

像用户在说明自己的工作被卡住了。先写现在的情况，再写要变成的行为，把边界和取舍写进同一段。

禁止出现：

- 文件路径、组件名、函数名、变量名、依赖包名
- 「技术栈约束」「架构约束」这类标签
- 五维评分、审核、G16、G19、收录门槛
- 「修改五个文件」「高内聚」这类出题元话术
- 彰显、培养、至关重要、格局、不可或缺、兜底、根因、收口、综上所述

版式对齐 `mb.md`，保持 170–380 字的原有检查范围，通常写到 170–240 字。优先写清当前行为、唯一目标、两项困难证据和一个会改变实现的边界。用一两句限定处理范围；不要为了凑字数新增兼容迁移、通用撤销、异步恢复或批量导出等要求。

22 条的用户目标互相分开。同一条交互不要换个名字再出一次。

## 埋缺陷

结构检查第一次通过之后，优先保留已发现且合格的真实缺陷；不足时再植入，最终恰好准备 2 个出题缺陷：

- 缺陷是运行时会走错的分支，不是注释里的 TODO。
- 用户能在界面上看出错误，干净状态下几步操作就能遇到。
- 正确修复要改至少 5 个文件；只改一个判断仍会有界面、播放、导出或重新打开后的结果对不上。
- 不要在注释、README 或提交说明里标明这是题目缺陷。
- 埋完重新运行类型检查、生产构建、结构检查和最终容器/界面验收。缺陷不能靠互相引用私有文件或复制五份同样错误来制造。
- 在两个独立的基线副本中分别复现并验证参考修复，保留至少五个必要业务文件的真实 diff、失败复现日志和修复后通过日志。参考修复不能混入题目基线；另一道题也必须能从同一原始基线复现。

写 Bug 题时重新打开相关文件。题目里的错误行为必须和代码一致。可以写一句用户能理解的原因，不写实现坐标。

## 必须留存的逐题验收

依照 [验收记录规范](references/acceptance.md)，将证据写入项目外的 `acceptance.json`，不能只存在于模型思考或临时口头说明。每题具备：

- 题目类别与源码依据；0-1 的不存在性搜索说明、迭代的已有行为、Bug 的真实错误分支。
- 至少两项困难特征的正文原句、实现含义和验收依据。
- 5–7 个业务文件的必要改动，以及否定更少文件合理方案的分析；直接改动的顶层功能模块最多 3 个。
- `scope` 中的现有复用能力、明确规模边界和排除的相邻功能；独立复核必须确认范围可控。
- 总计 2–3 个验收场景，含正常与关键边界；Feature/Bug 仍需动作到结果的数据流、失败/冲突策略和边界行为，可通过一个具体冲突边界体现，不能打包多个无关场景。
- 未参与出题的独立复核者逐题确认：真实难度为困难、两项特征成立、五文件必要、类别正确、目标不重复、不依赖其他题。

任何一项不成立就换题或补足真实业务范围后重审；不能把简单题重新措辞当作通过。复核结论不得由出题者代填。

## 检查

```bash
node <技能目录>/scripts/check-prompts.mjs <提示词文件绝对路径>
node <技能目录>/scripts/check-delivery.mjs <项目根> <提示词文件绝对路径> <项目外验收目录>/acceptance.json
```

第一项只检查数量、标签、版式、篇幅、禁词和重复/高度相似。第二项检查当前项目快照与证据完整性，并重跑静态预检。两者都不能凭关键词自动裁定真实困难。最终交付必须同时有真实运行结果与独立逐题语义与范围复核，任何一题未通过就不能把整套标为完成。
