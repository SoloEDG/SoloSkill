# 小范围困难题验收记录

最终交付要求：22 题全部真实困难，每题至少两项困难特征、5–7 个必要业务文件改动，并通过范围控制复核。此记录把证据留给独立复核者，不是填写“通过”即可获得资格的评分表。脚本检查记录结构、路径、源码摘录、快照和数量；无法证明填写者身份、日志真实性、参考修复正确性或真实难度。

## 文件与快照

在项目外建立 `.pinru-audits/{项目编号}/`，包含 `acceptance.json`、各次实际运行的日志、两个 Bug 的参考修复 diff 和独立复核原始报告。所有证据文件路径相对于这个验收目录，不能指向项目内部或越出目录。参考答案和验收资料不进入 Pinru 的初始仓库。

在最终源码与题目文件不再变化后执行：

```bash
node <技能目录>/scripts/check-delivery.mjs --fingerprint <项目根> <提示词文件>
```

将返回的 `projectSha256` 和 `promptSha256` 原样填入记录。项目快照包括源码、依赖锁和配置等全部文件，仅排除项目根的 `node_modules`、`dist`、`.git`、`coverage` 目录及单独计算哈希的当前题目文件。项目源码不使用符号链接。拿到哈希之后修改项目或题目会使验收失效；不能只刷新哈希而沿用旧日志、旧报告。最终独立报告也要写出所审的两个哈希。

## acceptance.json 顶层字段

| 字段 | 内容 |
| --- | --- |
| `schemaVersion` | 数字 `1` |
| `projectSha256`、`promptSha256` | 上述命令实际输出的哈希 |
| `checks` | 下列七项真实运行检查 |
| `projectReview` | 领域、纯前端、职责、内聚耦合和真实交互复核 |
| `review` | 独立复核者及原始报告 |
| `tasks` | 恰好 22 条逐题记录，无重复或缺失 id |

`checks` 必须有 `typecheck`、`build`、`structure`、`dockerConfig`、`dockerBuild`、`dockerSmoke`、`browserSmoke` 七个键。每项对象均包含 `status`、`action`、`log`：

```json
{"status":"pending","action":"npm run build","log":"logs/build.log"}
```

实际运行后才能把 `status` 改为 `passed`；失败为 `failed`、环境阻碍为 `blocked`、未执行为 `pending`，后三种均不能交付。`action` 写实际命令或浏览器操作，`log` 指向真实输出。命令日志包含命令、退出码、关键结果；重定向输出时保留真实退出码。浏览器日志包含 URL、操作、预期/实际、控制台检查和截图路径。`dockerSmoke` 包含容器状态、实际端口、首页/静态资源及路由验证；HTTP 成功不能替代 `browserSmoke`。

`projectReview` 包含：

- `domain`：固定为 `游戏图形与多媒体`，复核者确认产品确实属于此领域。
- `pureFrontend`：说明浏览器内的数据流、持久化方式及不存在业务后端的代码依据。
- `cohesion`：说明模块职责、共享数据所有权、公共接口以及没有跨模块规则堆积、循环或重复实现的依据。
- `responsibilities`：对象，键为实际 `src/features/` 模块名，值为各自职责说明。
- `interactions`：至少三个不同操作链的数组。每项包含 `from`、`to`（两个真实模块名）、`steps`、`expected`、`observed`、`log`；三条链路合计应覆盖全部模块，复杂链路可在步骤中补充中间模块并增加记录。

顶层 `review` 包含 `author`、`reviewer`、`independent`、`verdict`、`log`。两个身份填写真实子代理/人工标识；`independent` 只在复核者未参与出题时为 `true`。初始 `verdict` 为 `pending`，独立复核明确全部通过后才写 `pass`。原始报告保存在 `log` 对应文件，逐题结论由复核者提供，出题者只负责整理和回填，不得虚构。

## 每题记录

`tasks` 中使用这些稳定 id：`gen-01` 至 `gen-10`、`feature-01` 至 `feature-10`、`bug-01` 至 `bug-02`，按最终题面在各小节的位置对应。每条包含：

| 字段 | 内容 |
| --- | --- |
| `id` | 当前题目的稳定 id |
| `difficulty` | 真实难度必须为 `困难` |
| `goal` | 单一、可辨别、与其他题不重复的用户目标 |
| `categoryEvidence` | 0-1：搜索范围、现有接口和能力缺口；迭代：已有行为及扩展；Bug：实际错误分支与现象；说明本题不依赖别题完成 |
| `features` | 至少两项不同的困难特征，格式见下文 |
| `sourceEvidence` | 至少一个 `{ "path": "src/...", "quote": "当前源码的准确摘录" }`；覆盖关键链路，不用无关常量证明业务 |
| `changes` | 5–7 个不同文件，各为 `{ "path": "src/...", "action": "modify", "reason": "此处必要的业务变化及省略后不满足哪个验收点" }` |
| `minimality` | 尝试更少文件方案后的结论；具体说明改公共函数、复用接口、复用现有状态为什么仍不能完整满足此题 |
| `acceptance` | 合计 2–3 个场景，至少包含正常及边界两种场景，每项 `{ "kind": "normal", "steps": "步骤", "expected": "可观察结果" }`，边界的 kind 为 `boundary` |
| `scope` | 复用能力、数据边界与排除项，见下文 |
| `review` | 独立逐题结论，见下文 |

`changes.action` 为 `add` 或 `modify`，前者路径在当前基线尚不存在，后者必须存在。路径采用规范的项目相对路径和 `/`，不能含 `..`。仅业务 `.ts`、`.tsx`、`.vue` 计数，不含声明文件、测试、配置、样式、生成物或纯转导出。新建文件必须有新职责；不得拆碎函数凑五个。

`changes` 还可列出必要的辅助转导出，额外标记 `"counted": false`。只允许 `src/features/<模块>/index.ts` 或 `src/shared/index.ts` 的纯转导出改动；它们不占 5–7 个业务文件额度，也不能列入 `review.necessaryFiles`，但仍计入实际直接涉及的模块范围，且在 Bug diff 中不能漏报。默认未填写 counted 的文件均按业务文件计数。独立复核者必须检查实际代码/diff，确认这些入口只调整转导出，没有夹带执行逻辑、数据结构或业务规则；不能通过 counted:false 隐藏额外工作。其他非业务文件不列入 changes，仍随参考 diff 供复核者查看。

`features` 每项包含 `kind`、`quote`、`reason`。`kind` 仅从「多模块整合」「关键设计取舍」「复杂技术关注点」中选择；`quote` 必须准确摘录当前题面中完整的证明句，`reason` 结合基线解释它为何是实质困难。两个不同名词、无关的“保持不变”、简单二选一或关键词罗列均不成立。

每题 `scope` 包含以下三个字段，均根据当前题目填写：

- `reuse`：复用的现有业务源码路径数组，至少一个；路径必须存在且在本题 `sourceEvidence` 中有源码依据。只复用基础设施，不得把 0-1 的目标能力提前做好。
- `dataBound`：具体的数据规模或操作范围，例如“只处理当前角色的一条路线，最多 12 步”；题面要有一致的限制，不能只在验收记录中偷偷缩小需求。
- `excluded`：至少一个本题不扩展的相邻能力，例如“队伍多人同时规划”“跨回合自动执行”。只排除真正会扩张范围的功能，不列空泛口号。

每题 `review` 包含：

- `verdict`：独立复核通过后才为 `pass`。
- `scopeVerdict`：独立确认范围可控后为 `pass`；范围过大同样拒绝。
- `scopeReason`：说明只有一个闭合目标、5–7 个必要业务文件、最多三个直接改动的功能模块、2–3 个具体验收场景，复用底层能力且题面与规模边界一致；指出两项困难证据来自哪里。
- `actualDifficulty`：独立判断为 `困难`，不能沿用题面的标签。
- `featureKinds`：复核者确认成立的至少两个特征名，必须出现在该题的 `features` 中。
- `necessaryFiles`：复核者确认不可省略的至少五个文件路径，必须属于该题的 `changes`。
- `reason`：判断实际工作量、两项特征、类别、任务独立性和用户目标的依据。
- `shortcutAnalysis`：复核者主动寻找一到四文件的完整正确解法，以及该解法为何不成立；存在这样的方案时本题不通过，不能把其余改动作为“顺便优化”凑数。

若必要性有争议，在隔离副本尝试参考实现并保存真实 diff/验证，再交独立复核。不确定不能填写通过。

## Bug 题附加证据

两个 Bug 记录额外包含 `bug` 对象，字段是 `steps`（从干净基线复现）、`actual`、`expected`、`reproductionLog`、`referencePatch`、`verificationLog`。实际与预期必须不同。

- 先在最终基线复现错误，再在它的隔离副本应用修复并验证。日志记录两边结果、正常及边界场景，以及另一道 Bug 不影响本题复现的检查。
- `referencePatch` 是真实 Git 格式 diff（含 `diff --git a/... b/...` 和有效增删行）。检查环境需要 Git；最终脚本使用 Git 解析真实路径，在隔离副本执行 `git apply --check`，核对格式及对当前基线的可应用性，不修改最终项目。中文和空格路径可使用 Git 默认转义。5–7 个业务文件必须存在实质改动，并在 `changes` 中说明；空 diff、注释或格式化凑数不成立。
- 独立复核者检查修复是否必要、是否正确，以及能否通过更少文件实现。不得把样例测试夹具中的合成日志当成项目运行证据。
- 两份参考修复各自从同一原始基线开始，不串行依赖；最终题目项目保留待修缺陷，不包含答案、测试结果标记或说明缺陷的注释。

## 独立复核任务

提供最终项目路径、题目路径、验收目录和两个快照哈希，要求未参与出题的复核者实际读代码及日志，逐题判断，不给出预设“通过”结论。至少执行：

1. 核验最终项目领域、纯前端、25 个真实业务文件、模块职责、三条交互、类型检查/构建及容器/浏览器日志。
2. 逐题检查类别是否成立、实际难度是否困难、两项特征是否实质存在、五个文件是否必要，以及是否从同一基线独立可做。
3. 主动提出更简单实现；能用少于五个文件完整解决、只是文案/样式/配置、小字段增删或拼凑小改的题目一律拒绝。
4. 核对两道 Bug 的源码、复现、真实 diff 和修复后结果；有疑问就在隔离副本重放，不修改最终基线。
5. 按 [范围控制规则](compact-scope.md) 检查每题是否一个目标、5–7 个必要业务文件、最多三个直接改动模块、2–3 个验收场景；即使数量合格，也拒绝在五个文件内实现新引擎、多个算法或大量兼容分支的题目。检查 22 个目标是否重复或换名重述，按 id 输出 pass/fail、证据和修改意见。任何一题不能确认时整体不通过。

复核报告和逐题记录一致后执行 `check-delivery.mjs`。证据缺失或环境受阻保持待验收，保留成果并完成其余工作，不降低困难标准。脚本通过与独立报告通过都不能由出题者凭空宣称。

## 维护本技能时的回归

用包含 TypeScript 编译器 API 和 `@vue/compiler-sfc` 的工具依赖目录运行：

```bash
SKILL_TEST_NODE_MODULES=<工具依赖目录>/node_modules node --test <技能目录>/tests/*.test.mjs
```

测试夹具是为验证检查器制作的合成材料，不代表真实项目或 22 道题已经验收。
