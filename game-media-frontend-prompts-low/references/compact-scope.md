# 困难档内控制工作量

本版本保留困难档、至少两项困难特征、至少五个必要业务文件等全部底线，选择实现范围有限、依赖现有能力的题目。执行成本主要通过减少状态组合、新技术机制和相邻需求来控制，不用降低标签、减少文件或牺牲架构换取速度。模型完成时间还取决于基线质量、模型和运行环境，不能保证固定分钟数。

## 每题的范围

| 项目 | 规则 |
| --- | --- |
| 用户目标 | 一个独立、完整、可观察的业务结果 |
| 困难特征 | 至少两项；优先真实的多模块整合 + 一个关键设计取舍，不要求把第三项也做成新难点 |
| 业务文件 | 必要实质改动 5–7 个；目标靠近 5 个；不计测试、配置、样式、文案和纯转导出 |
| 功能模块 | 优先两个，最多直接改动三个现有顶层模块；app/shared 文件计入业务文件数，不当成功能模块 |
| 验收场景 | 2–3 个：一个正常闭环、一个关键边界，确有必要再加一个失败/冲突场景 |
| 数据范围 | 明确限定当前角色、单场景、单片段或有限集合；按产品指定实际数量或范围 |
| 技术基础 | 复用基线的渲染、播放、计算、状态和存储，不新增专业技术底座 |

必要的公开入口纯转导出按验收规范记录为不计数辅助改动，不能算作第五个业务文件；复核者检查它确实只有转导出。

上述上限是选题门槛。如果正确实现需要八个业务文件，先缩小目标或换题，不能删掉必要改动、合并职责、压成巨型文件或漏报影响面。验收条目中每条只描述一条具体操作链，不能把十个场景藏在一个数组项里。复核者同时看语义工作量，不能只数文件或场景。

## 三类题怎么收敛

- **0-1 代码生成：**新增一个现有模块尚不具备的完整业务能力，接入另一模块的数据或输出。复用入口、渲染和状态基础设施；不要求新建完整应用、通用平台、插件系统或第六个顶层模块。新增能力必须可独立验收，不能只有按钮或字段。
- **Feature 迭代：**只改变已有流程中的一个规则或一种操作方式，明确与一个相关模块如何一致。仅处理本题必须遇到的失败/冲突及边界；不要顺便加入批量操作、历史回滚、格式升级、性能重构和新导出格式。
- **Bug 修复：**选择一个稳定复现、跨模块状态契约不一致的缺陷。在现有架构下，修复涉及 5–7 个有各自职责的业务文件。仍必须提供复现、参考修复和验证；不要串联几个独立小 Bug，也不要复制五处同样的错误凑数量。

优先选择已有标识、选择状态、临时预览与提交、局部范围和共享业务规则之间的具体一致性问题。若只改一个公共函数就能正确完成，题目不满足文件门槛，应换题，不把额外 UI 改版或测试文件计入。

## 不在单题中叠加的工作

选题不新增多人协作、云同步、离线队列、权限系统、多版本迁移、通用撤销重做框架、跨格式编解码、新物理/渲染引擎、全应用架构重构，或要求自研一套专业算法。项目基线已经具有其中某种能力时，可以复用它完成一个局部业务变化；只验证本题实际触达的链路，不扩建整个机制。

复杂技术关注点确有必要时，限定一个具体过程，例如已有缩放条件下的坐标映射、已有播放流程与手动选择分离、单次异步加载结果过期处理。正文必须交代触发和保证的结果；仅添加“播放、并发、兼容”等词仍不算困难。

项目级 Docker、类型检查、架构规则由基线及技能流程统一落实，不在每一道题面里要求重新搭建工程。题面写用户能观察的行为与范围，不要求附加技术报告、重建测试平台或无关全局优化。

## 示例：一个移动规划闭环

假定战棋基线已经支持选中角色、计算可达路线、扣减行动点、绘制地图和显示角色状态，以下是新增能力的候选题面：

> 现在点击地图中的可达格子就会立即移动角色，选错终点后无法提前调整。希望增加移动前的路线预览，限定当前回合选中的一个角色，路线最多十二步，地图显示路径，角色面板显示预计剩余行动点。可以直接移动后再撤回，也可以只保存临时计划，这里选择后者，代价是需要单独维护待确认路线，但取消不会改变真实位置和行动点。确认时重新检查角色位置、行动点和路径是否仍然有效，条件变化则取消计划并提示重新选择；切换角色也取消计划。确认成功后地图位置和角色面板一起更新，本次不增加队伍多人规划或跨回合执行。

真实困难证据是地图与角色状态的交接，以及临时计划/即时修改回滚之间的状态设计取舍。实现复用已有寻路和绘制能力，只做一条“选择—预览—确认或取消”链路。

候选涉及的职责可以是计划数据、角色规则、角色状态展示、地图交互和路线显示；这不是预设五个文件答案。必须对实际项目核对职责及修改必要性。如果实际源码通过少于五个文件即可完成，就换题；如果需要重建寻路器或跨四个模块，就换一个范围更小的目标。

## 出题与复核顺序

1. 先列 22 个不同用户目标及每题复用的基线能力，确保独立可做，不依赖先完成另一题。
2. 用实际源码列出 5–7 个必要业务文件和最多三个直接改动模块，找出两项真实困难证据。
3. 写 2–3 个具体验收场景，指定数据边界及不扩展的相邻能力，再写 170–240 字左右的题面；原格式允许范围仍为 170–380 字。
4. 独立复核同时判断困难底线和范围上限。不足困难就换题；超过范围也换题。不能用增加无关需求抬高难度，或用漏报文件压低工作量。
5. 复核一次需要提供足够源码依据。只有两道 Bug 必须在隔离副本完成参考修复；其余题目在文件必要性或难度存在具体争议时才试做参考实现，不默认把全部 22 题再实现一遍。

需要确认每题的范围，不需要为每题写长篇设计方案。使用既有验收记录里的目标、源码依据、文件必要性与正常/边界场景；只额外填写 `scope` 和独立范围复核结论。
