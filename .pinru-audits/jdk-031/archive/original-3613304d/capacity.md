## 基线能力（实现后必须具备，题目不得再当成缺口）

- 五模块：`site` 观测位置、`clock` 时间控制、`sky` 星空显示、`catalog` 天体检索、`plan` 观测清单。
- 地点含纬度、经度、时区与若干城市；时刻含民用时间输入、暂停/播放、倍率与步进。播放用帧间隔累加模拟时刻，单帧最多计入 0.1 秒，避免后台卡住后一次跳过整夜。
- 星图按地点与模拟时刻把恒星、太阳、月亮和五颗行星投到圆穹上。拖动改变视线，滚轮改视场。点选天体后把视线对到该方位；很低或在地平线下时视线落在高度 28°、方位仍指向它。
- 检索按中文名、英文名过滤，并把结果定位到星图。
- 清单按加入顺序保存目标，用几何高度是否大于 0° 标「地平线上 / 地平线下」，并用十分钟后的高度差标升起或落下。可新建、改名、切换多份计划。
- `localStorage` 整份保存地点、倍率、模拟时刻和清单。播放中约每两秒写一次，地点或清单一改就写。不保存视线和点选。刷新后播放是停的，模拟时刻保留。没有 `storage` 监听，没有分字段合并。
- 坐标是几何高度方位，不含蒙气差、时钟偏差、方位零点、画面拧转、地平遮挡、子午线翻身或停留排程。

降低难度的已有能力核对：

- 有单一模拟时钟和播放倍率，但没有第二套对照时刻，也没有租赁或写作者身份。新增停留排程不能把播放倍率当成观测耗时。
- 没有跨模块事件总线。定位、加入清单、换地点都由壳层调用各模块公开函数。
- 持久化是整份 JSON 覆盖，不是可合并文档，也没有撤销栈。
- 点选只有一个 `selectionId`。没有假设集合、没有遮挡多边形、没有必看标记。

## 模块交互（基线至少三处）

1. 改地点或改时刻 → 星图重算高度方位 → 清单的可见与升降一起变。
2. 检索或清单点「定位」→ 星图把该天体放入视线并画上选中环。
3. 星图点选 → 检索高亮同一颗 → 可加入当前清单；保存后刷新，清单和地点还在，视线回到默认。

## 候选

四题从同一基线独立完成，用户目标不重叠。

### gen-01 多假设认星

- 类别：0-1。目标：连续把计算星拖到肉眼位置，在时钟偏差和方位零点尚未分清时保留多套假设。
- 基线：点选只改视线，不改正坐标。
- 可复用：赤道到地平、投影、清单可见性、地点切换、播放。
- 最强常规方案：两颗星立刻做一次最小二乘，把唯一偏差写进换算，第三颗在改过的星图上点。
- 常规方案未解决：前两颗容差内可以有两套解。先采纳其中一套会移动第三颗的原始方向，把仍然成立的另一套判丢。换地点后方位零点若跟着走，会转掉另一个屋顶；时钟偏差若不跟着走，新地点对过的钟不能带回原地点。
- 剩余决策：假设何时写入星图、定位和清单共用的换算；采样保持在未改正的地平方向，还是保持在已经套用某一套假设的画面上。
- 反例：两套假设都能套上前两颗。先套用第一套再点第三颗，第二套被错误淘汰。正确做法是第三颗仍按原始方向检验每一套，只剩一套时三处一起改。
- H3：提交边界决定下一笔采样落在哪个坐标系，不是多存一个角度字段。

### gen-02 圆顶狭缝与线缆缠绕

地平遮挡多边形在复核前被替换：单值地平函数失败后，地平坐标里的笔画加月面采样可以直接满足原候选，常规组合已经够用。新目标不再画任意遮挡。

- 类别：0-1。目标：圆顶狭缝按有限转速跟踪当前星，线缆允许的转角大于一整圈。
- 基线：没有狭缝、转速、限位或未展开方位。可见性只有「地平线上 / 地平线下」。视线拖动不改变天体方位。
- 可复用：播放的模拟时刻、点选、地点切换、清单文案、整份保存。
- 最强常规方案：每帧把狭缝方位收到离目标更近的可停位置；或者选定一侧后永远不换。换地点时把狭缝角度清零。
- 常规方案未解决：始终挑更近的一侧，会把正北附近的连续小移动当成跨线缆的空转。始终不换侧，会在改选、换地点或拨时之后顶到限位，星仍在地平线上。把角度清掉等于跳过缠绕，和「换地点不能清掉已转角度」冲突。
- 剩余决策：连续跟踪与断开后的重选分界在哪里；两侧都会顶住时如何比较被挡住的时长。题面只给两种一律策略的失败现象，不写状态机。
- 反例：狭缝停在高位缠绕、星从方位 358° 走到 2°。最近侧策略空转将近一圈。改选一颗后半夜会顶到限位的星，不换侧则会在落下前跟丢。
- H3：同一种「最近侧」规则不能同时保住过正北的连续跟踪和断开后的后半夜跟踪。分界本身要推导。

### feature-01 最晚可开始的停留

- 类别：Feature。现状：清单只标此刻是否高出几何地平，以及十分钟升降，不安排一段停留。
- 目标：在当晚找出最晚的一段连续停留，使必看目标都能在约束内看完，并给出顺序见证。
- 可复用：几何位置、太阳月亮位置、播放（只负责预览，不负责排程耗时）、清单顺序。
- 最强常规方案：按落下先后贪心，或对起点二分再套贪心顺序。十六颗目标做全排列会卡住星图。
- 常规方案未解决：可行性对起点不是单调的，中间一段不可行、更晚一段又可行。翻越子午圈要花额外时间，而且翻身与否取决于到达时望远镜停在哪一侧，不能收成固定路程表。只保留「最早到达某目标」会剪掉较晚但侧向正确的走法。
- 剩余决策：搜索状态至少要能区分到达时刻和望远镜侧向；如何在十六颗规模下给出最晚可行起点或证明排不开，同时星图播放不被一次搜索冻住。
- 反例：贪心先去西边高目标，翻身后赶不回东边短窗口；实际上一直留在东侧可以看完。起点二分会落在两段可行之间的空档，误报排不开。
- H3：剪枝维度和侧向状态会影响是否还存在更晚的可行停留，不是把现有可见标记再写一遍。

### feature-02 两个窗口共用一次观测

- 类别：Feature。现状：刷新可恢复地点、时刻和清单；播放约每两秒整份覆盖保存。
- 目标：两个窗口同时开着时，走时不再冲掉另一边刚改的清单，暂停的一边能跟上对方的走时，但正在播放的星空不被旧的走时写回过去。
- 可复用：整份本地保存、帧间隔累加、清单成员函数、地点校正。
- 最强常规方案：谁后写入整份 JSON 就听谁的；或两个窗口都忽略对方。
- 常规方案未解决：整份后写覆盖会让走时冲掉清单增量。只取较晚的模拟时刻会拒绝用户把时间往回拨。播放中的窗口若采纳对方每一个走时，两边会来回跳。后台标签被节流后补写一笔旧时刻，会把前台已经走完的星空拉回去。
- 剩余决策：走时写入和用户改时如何区分；清单增删与改名冲突时合并到哪一份；视线为什么不能进共享记录。
- 反例：甲正在播放，乙删掉一颗并加入另一颗。甲下一次走时若整份覆盖，乙的清单改动消失。乙把时刻往回拨，若甲只接受更晚的时刻，这次回拨不会生效，星图仍停在未来。
- H3：时钟所有权、用户改时和清单合并是同一次保存里的不同提交规则，整份覆盖或单值比较都不能同时满足。
