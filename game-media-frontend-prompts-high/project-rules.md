# 项目实现规则

## 题材

只做游戏图形与多媒体。画面、序列帧、时间轴、镜头、图块、精灵、粒子、着色预览、波形、音效和谱面都属于这个范围。

允许清单（每次只做其中一个完整产品）：

- 序列帧动画台：镜头、图层、时间轴、预览播放、导出
- 瓦片关卡台：图块库、图层、碰撞、实体摆放、小地图
- 音效剪辑台：波形、区间、多轨、包络、预览与导出
- 节奏谱面台：波形、判定线、音符、节拍、试玩
- 粒子效果台：发射器、力场、贴图、时间轴、场景预览
- 过场分镜台：立绘、台词、镜头、声轨、预览播放
- 精灵图集台：切片、锚点、动画片段、打包、预览
- 材质预览台：贴图槽、参数、预览模型、动画、截图对比

不要做电商、后台、博客、通用表格，也不要做与画面或音频无关的管理工具。用户指定像素画时才做像素画，并且 22 条题目不能复述 `mb.md`。

## 模块

做 4 个或 5 个功能模块。每个模块有自己的界面、状态操作和规则，读一个模块就能知道它负责什么。

模块之间要能互相影响，但只能通过共享的文档数据和少量公开命令交互。例如：时间轴决定画面正在编辑哪一帧，调色结果被预览和导出同时使用，播放头不能偷偷改掉用户选中的对象。基础项目里至少要有 3 处这种真实交互，后面的题目继续加交互。

目录固定为：

```text
src/
  app/                  # 壳、布局、命令路由
  shared/               # 文档类型、纯数据操作、跨模块命令类型
  features/<module>/
    index.ts            # 唯一公开入口
    model/              # 该模块的状态与规则
    lib/                # 该模块的纯计算
    ui/                 # 该模块的界面
```

约束：

- `shared` 只放文档形状和跨模块纯函数，不放某个模块的界面，也不引用 `features` 或 `app`。
- `features` 不引用 `app`。
- 功能模块、app 或其他源码引用功能模块时，只能引用对方的 `index.ts`；同模块内部除外。禁止绕过入口引用对方的 `ui`、`model`、`lib`，禁止文件和模块循环依赖（包括类型依赖）。
- `app` 引用每个模块的公开入口，并把它们装进同一个工作区。
- 每个模块都要读写 `shared` 里的文档或命令，不能做成五个互不相干的演示页。
- 领域计算放在 `lib` 或 `model`，不要堆进组件。
- 单个业务文件不超过 400 行。超过就按职责拆开。
- 不要用空文件凑数量。除 `index.ts` 外，业务文件应有实际类型、规则或界面。

## 业务文件

计入业务文件的是 `src` 下的 `.ts`、`.tsx`、`.vue`。不计入 `*.d.ts`、测试文件、`node_modules`、构建产物，以及 `vite.config.ts`、`tsconfig`、Docker 和 nginx 配置。

业务文件总数不得低于 25。每个功能模块至少 4 个业务文件。目标是 28 到 40 个有职责的文件，而不是把一行函数拆成一个文件。

## 技术栈与容器

- React 项目使用 Vite、React、TypeScript。Vue 项目使用 Vite、Vue 3、TypeScript。同一个项目不要混用两套界面框架。
- TypeScript 对所有业务源码开启有效严格模式。提供独立的 `npm run typecheck`（React 使用 tsc，Vue 使用 vue-tsc）和 `npm run build`；仅 Vite 构建不能代替类型检查。
- 别名统一声明在 tsconfig，Vite 配置与其一致；模块加载使用可静态解析的路径。结构检查从项目依赖加载 TypeScript 编译器 API；采用无此 API 的 TypeScript 版本时，额外安装兼容解析器 `@typescript/typescript6`。Vue 项目提供 `@vue/compiler-sfc`。
- 纯前端。容器里只托管构建后的静态文件。保存与交换数据使用浏览器本地存储或用户下载的文件，不新增业务 API。
- 提供 `Dockerfile`、`docker-compose.yml` 和 `nginx.conf`。镜像先构建静态资源，再用 nginx 提供，`try_files` 回到入口文件。
- `docker compose up --build` 后，浏览器能打开工作区。
- README 只写安装、本地启动和 Docker 启动。不要写题目答案、模块评分或故意留下的缺陷。

结构检查：

```bash
node <本 skill 目录>/scripts/check-cohesion.mjs <项目根>
```

静态检查会解析导入、别名、配置和依赖环；它不证明界面已挂载或模块真正交互。`import type` 不算运行时挂载，公共类型共用也不算交互。逐个检查模块职责、共享数据所有权和完整操作链；有模块把别的模块规则写进组件、共享层包揽全部业务或无关文件凑数时先修复。

## 最终运行验收

验收对象必须是保留两处待修缺陷、供所有题目使用的同一个最终源码快照。修改源码、依赖或容器配置后，旧通过日志失效。

1. 执行 `npm run typecheck`、`npm run build`、结构检查，记录真实命令、退出码和输出。
2. 执行 `docker compose config`、`docker compose build`，再启动当前项目容器。使用本任务独有的 compose 项目名，避免覆盖已有服务；日志保留在项目外。
3. 检查容器状态及实际发布端口，访问首页和静态资源；有前端路由时验证刷新与深链接，不能只凭镜像构建成功判定可运行。
4. 浏览器验证工作区及至少三处不同的跨模块交互，记录操作、预期、实际结果和截图/测试日志。仅收到 HTTP 200 不能证明 UI 可用。两个预定缺陷分别复现，其余核心链路不得报错或白屏。
5. 每个模块都要参与真实交互；至少三条链路可以覆盖多个模块。逐题核对后续迭代会怎样沿这些数据流影响其他模块。
6. 清理本任务启动的测试容器，保留日志；不删除用户既有服务、卷或数据。

Docker 不可用、容器不能启动或浏览器不可用时，记录具体阻碍并保持待验收。不得把“文件存在”“静态检查通过”“没有执行”填写成运行验证通过。
