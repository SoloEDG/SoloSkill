# 游戏图形前端项目与困难题

先创建可运行的纯前端项目，再基于最终源码交付 22 道真实困难题。所有题目的标签和实际难度都必须是「困难」。任意一题证据不足、存在更简单的正确实现或尚未独立复核，整套结果保持「待验收」，继续修正；不能降低难度、缩减数量或只改标签交付。

开始前读 [project-rules.md](project-rules.md)、[prompt-rules.md](prompt-rules.md)、[验收记录规范](references/acceptance.md)。模板优先用用户指定的 `mb.md`，其次当前工作区的 `mb.md`，没有时用 [随技能附带的模板](references/mb.md)。模板只规定数量和版式，不证明其中例题的难度，也不要复述像素画题面。

## 必须保持的约束

- 项目只属于游戏图形与多媒体；4 或 5 个独立功能模块，基础项目至少 3 处真实跨模块交互。
- React 或 Vue 3 + TypeScript + Vite，纯前端，无业务后端；Docker 容器提供静态页面。
- 至少 25 个有实际职责的业务源文件；创建后执行结构检查及人工职责复核，高内聚低耦合不通过就先修项目。
- 10 条 0-1 代码生成、10 条 Feature 迭代、2 条 Bug 修复，全部真实困难；每题实质满足三类困难特征中的至少两项。
- 每题正确实现需实质新增或修改至少 5 个业务源文件，且每处都有独立必要性。测试、配置、锁文件、生成物、纯样式、文案或转导出凑数不计。
- 题目基于同一个冻结的初始项目，彼此独立，不依赖先完成其他题；22 个用户目标不能重复。

## 开始前补齐缺口

沿用用户给出的编号、框架、题材。缺少项目编号时只询问编号（小写字母前缀加三位数字，如 `jdk-001`）；框架默认 React + TypeScript + Vite，题材从项目规则中选择。项目放在当前工作区的 `{项目编号}/`，已有目录时检查是否为本任务的可续做产物，不能覆盖不明已有内容。

在项目外建立 `.pinru-audits/{项目编号}/` 存放验收记录、运行日志、参考修复和独立复核报告；它不是题目仓库的一部分，不能复制到评测初始环境。题目根目录只放 `{项目编号}_提示词_{MMDD}.md`，日期使用用户所在时区的执行当天。

## 执行顺序

1. 选定产品、模块职责和真实交互，规划能支撑 22 道不同困难题的基线能力与空白能力。不要先拼满简单题再补困难措辞。
2. 按项目规则实现项目和 Docker 配置，安装依赖，执行类型检查、生产构建、结构静态预检。

```bash
npm run typecheck
npm run build
node <技能目录>/scripts/check-cohesion.mjs <项目根>
```

3. 实际打开界面，逐一验证各模块职责及至少 3 条交互链；检查业务规则归属、共享状态和公开接口，避免通过巨型共享对象或重复计算掩盖耦合。未通过时修复并重跑，通过前不写题目。
4. 按提示词规则准备恰好两个可复现的真实行为缺陷。原项目已有符合条件的缺陷就使用已有缺陷，否则植入。保持模块边界，不制造构建失败；不要为达到五文件门槛复制错误逻辑。
5. 在隔离副本中分别验证两个 Bug 的参考修复：先复现错误，再验证修复及相关交互，保存真实 diff 和日志。最终基线保留待修缺陷，不能把参考答案合回项目。
6. **对植入缺陷后的最终源码重新运行**类型检查、生产构建、结构检查、Docker 配置校验、镜像构建、容器启动与浏览器冒烟验证。按 [运行验收要求](project-rules.md) 留存日志；缺陷复现是预期失败，其余工作区流程必须可用。任何后续源码修改都使旧验证失效。
7. 阅读最终源码，逐题编写需求和 [验收记录](references/acceptance.md)。0-1 记录搜索范围及确实不存在的能力；迭代记录现有行为；Bug 记录实际错误分支、复现与参考修复。每题必须说明两项困难证据、至少五个文件的必要性，以及为什么更少文件的正确方案不成立。
8. 写入 22 题文件并执行格式预检。失败时按真实问题修改，不能为触发词表填充无关要求。

```bash
node <技能目录>/scripts/check-prompts.mjs <提示词绝对路径>
node <技能目录>/scripts/check-delivery.mjs --fingerprint <项目根> <提示词绝对路径>
```

9. 将快照哈希录入项目外的 `acceptance.json`。委派未参与出题的独立子代理，读取完整项目、22 题、运行日志和逐题证据，按 [验收规范](references/acceptance.md) 复核并产生报告。不得替复核者预填通过结论。无子代理能力时需要独立人工复核，在获得结果前状态为待验收。
10. 任何一题被判中等、简单、困难证据不足、文件数不必要或类别不真实，必须换题/改题，重新核对类别、去重、快照及逐题证据。项目修改时重做受影响的验证并取得针对新快照的独立复核；不能沿用旧通过记录。
11. 独立复核全部通过后，执行最终记录检查，它会重新运行两项静态预检并核对当前快照。

```bash
node <技能目录>/scripts/check-delivery.mjs <项目根> <提示词绝对路径> <项目外验收目录>/acceptance.json
```

**完成条件同时满足：最终代码实际验证通过、22 题独立语义复核全通过、最终记录检查通过。** 三者缺一就继续修正或明确报告具体待验收项，不能宣布全部合格。脚本只能检查结构和证据一致性，不能代替真实难度判断，也不能证明填写者身份或日志真实性。

## 完成时报告

简述项目路径、技术栈、模块职责、22 题文件路径，以及类型检查/构建/Docker/交互验证和独立复核结果。给出项目外验收记录路径供用户复核，题面中不泄露答案、源码坐标或评分术语。环境缺少 Docker、浏览器或独立复核能力时，清楚说明尚未通过的门槛；保留产物并继续可完成的工作，不能把缺失验证记成通过。
